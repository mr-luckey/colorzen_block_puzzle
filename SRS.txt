## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification (SRS) document defines the complete functional, non-functional, UI/UX, and architectural requirements for **ColorZen: Block Puzzle** — a mobile casual puzzle game for Android and iOS built with Flutter. This document serves as the single source of truth for all development, design, testing, and release decisions. A developer reading this document must be able to build the entire application with zero ambiguity.

### 1.2 Scope

**ColorZen: Block Puzzle** is a casual hyper-casual mobile game in which players drag and drop colored block pieces onto a 9×9 grid. Completed horizontal or vertical lines are cleared, scoring points. The game features:

- Three game modes: Classic (endless), Daily Challenge (seeded global puzzle), Zen (score-free relaxation)
- Procedural piece generation with provable fairness
- Three unlockable visual themes
- Local progress persistence via Hive
- Monetization through AdMob (interstitial + rewarded) and a Remove Ads IAP
- Shareable Daily Challenge result cards

**Out of Scope:**
- Multiplayer or real-time online features
- Server-side leaderboards (v1.0; local only)
- User accounts or cloud sync
- Piece rotation
- Undo functionality
- Timer-based game modes

## 2. Overall Description

### 2.1 Product Perspective

ColorZen: Block Puzzle is a standalone mobile application. It is a greenfield product developed by AppWareTech, designed specifically to capture market share from existing block puzzle games (e.g., Block Puzzle Jewel, Wood Block Puzzle, 1010!) by solving the top player pain points identified in competitor reviews:

| Competitor Pain Point | ColorZen Solution |
|----------------------|-------------------|
| Mid-game ads | Ads shown ONLY on game over screen, never during gameplay |
| Rigged piece feeling | Always visible "next 3 pieces" preview tray for planning |
| No undo (frustration) | No undo — intentional, preserves skill feel and tension |
| No progress save | Hive persistence saves on every piece placement |
| Timer pressure | Zero timers — pure zen, relaxed gameplay |
| No theme choice | Three unlockable visual themes |
| Repetitive levels | Procedural generation — 1000+ unique configurations |
| No daily habit loop | Daily Challenge mode with sharable result card |

The application runs entirely offline (except for ad serving). No backend server is required for v1.0.

### 2.3 User Classes and Characteristics

**Primary User: Casual Mobile Gamer (Ages 18–35)**
- Plays in short sessions (5–15 minutes) during commutes, breaks, or before sleep
- Expects intuitive controls — no tutorial needed
- Values visual polish and satisfying feedback
- Sensitive to disruptive ads
- Global audience; South Asian market focus requires culturally resonant themes (Desi Rangoli)

**Secondary User: Younger Player (Ages 8–17)**
- Attracted by bright colors and simple rules

- Prefers relaxed gameplay without pressure

**All users share:**
- Touchscreen-only interaction model
- Portrait orientation preference

## 3. System Features (Functional Requirements)

> **Requirement notation:** Each requirement is assigned a unique ID: `FR-[AREA]-[NNN]`.

---

### 3.1 Core Game Engine

**FR-ENG-001:** The game grid SHALL be a 9×9 matrix of cells. Each cell is either empty (`null`) or occupied by a `BlockColor` value.

**FR-ENG-002:** The player SHALL interact with the game exclusively through drag-and-drop gestures. No keyboard, no button-based placement.

**FR-ENG-003:** When a piece is dragged onto the grid, the system SHALL display a valid drop preview (ghost highlight) showing where the piece would land if released at the current finger position.

**FR-ENG-004:** The ghost preview SHALL show in the piece's color at 40% opacity when the placement is valid.

**FR-ENG-005:** The ghost preview SHALL show in red (`#FF4444`) at 30% opacity when the placement is invalid.

**FR-ENG-006:** A piece placement is valid if and only if ALL cells the piece would occupy are currently empty.

**FR-ENG-007:** On valid release, the piece SHALL be placed permanently on the grid. There is no undo.

**FR-ENG-008:** On invalid release, the piece SHALL animate back to its original position in the tray with a horizontal shake animation (±8px × 3 oscillations, 200ms total).

**FR-ENG-009:** When a player is holding a piece, the piece visual SHALL be offset 20px above the finger center so the piece is not hidden behind the user's finger.

**FR-ENG-010:** The game ends when no piece in the current 3-piece tray can be placed anywhere on the grid. The system SHALL check this after every piece placement.

**FR-ENG-011:** Game over detection SHALL check all three current pieces against all possible empty cell positions. If any piece has at least one valid placement, the game continues.

**FR-ENG-012:** The game SHALL save state to Hive after every successful piece placement (not just on app close).

**FR-ENG-013:** On app launch, the system SHALL restore the game to the exact saved state including grid, pieces, score, and mode.

---

### 3.2 Piece Generation System

**FR-GEN-001:** The piece pool SHALL consist of exactly 20 predefined shapes (see Appendix A for complete shape library).

**FR-GEN-002:** Each piece SHALL have a shape (2D boolean grid, max 4×4) and a single `BlockColor` assigned.

**FR-GEN-003:** The player SHALL always have exactly 3 pieces in the current tray.

**FR-GEN-004:** A "next pieces" preview tray SHALL display the next 3 pieces the player will receive after placing all 3 current pieces.

**FR-GEN-005:** New pieces are generated in sets of 3. A new set is generated when the tray becomes empty (all 3 pieces placed).

**FR-GEN-006:** Piece colors SHALL satisfy the fairness guarantee: within every batch of 9 consecutively generated pieces, all 6 `BlockColor` values appear at least once. This prevents any one color from being absent for too long.

**FR-GEN-007:** Piece shapes SHALL be selected using a weighted random algorithm that prevents the same shape from appearing more than twice within a 9-piece window.

**FR-GEN-008:** In **Classic Mode**, the piece PRNG seed SHALL be system random (unpredictable).

**FR-GEN-009:** In **Daily Challenge Mode**, the piece PRNG seed SHALL be derived deterministically from the current date string formatted as `yyyy-MM-dd`. The same seed produces the same sequence globally for all players on the same date.

**FR-GEN-010:** In **Zen Mode**, piece generation SHALL be identical to Classic Mode (system random).

**FR-GEN-011:** The system SHALL pre-generate all 6 pieces (3 current + 3 next) at game start and maintain this buffer at all times.

---

### 3.3 Line Clear Detection

**FR-CLR-001:** After every piece placement, the system SHALL scan all 9 rows and all 9 columns for complete fill (no empty cells).

**FR-CLR-002:** A row or column is "complete" when all 9 cells in it are occupied by any `BlockColor` value.

**FR-CLR-003:** All complete rows and columns SHALL be cleared simultaneously in a single clearing event.

**FR-CLR-004:** The system SHALL calculate the score multiplier based on how many lines are cleared in the single event (see Section 3.4).

**FR-CLR-005:** After clearing, the grid state SHALL be updated immediately. Cleared cells return to `null`.

**FR-CLR-006:** The line clear animation SHALL play concurrently with the score update, not sequentially.

**FR-CLR-007:** The system SHALL detect if a cleared line qualifies for the Color Bonus: if ALL cells in a cleared line are of the same `BlockColor`, that line's score is multiplied by 2.

**FR-CLR-008:** Multiple lines cleared simultaneously each independently qualify (or not) for the Color Bonus. Bonuses stack multiplicatively.

---

### 3.4 Scoring System

**FR-SCR-001:** Base score values per clearing event:

| Lines Cleared | Base Points |
|--------------|------------|
| 1 line | 100 |
| 2 lines | 250 |
| 3 lines | 450 |
| 4 lines | 700 |
| 5+ lines | 700 + (lines - 4) × 200 |

**FR-SCR-002:** Color Bonus multiplier: if a cleared line contains only one color, multiply that line's base contribution by 2.0×.

**FR-SCR-003:** Combo Multiplier: if the player clears at least one line in 3 or more consecutive moves, a combo is active. The combo multiplier is 1.5× and applies to ALL lines cleared while the combo is active.

**FR-SCR-004:** The combo counter resets on any move that does NOT result in a line clear.

**FR-SCR-005:** Score formula per clearing event:
```
event_score = (sum of per-line scores with color bonuses) × combo_multiplier
```

**FR-SCR-006:** The current score SHALL be displayed in real-time and updated immediately after each clearing event.

**FR-SCR-007:** Personal best score SHALL be stored per game mode (Classic, Daily) independently.

**FR-SCR-008:** In Zen Mode, no score is calculated or displayed. The scoring engine is disabled.

**FR-SCR-009:** When a new high score is achieved, the "BEST" label SHALL display a gold shimmer animation (1200ms sweep, repeated 3 times).

**FR-SCR-010:** A floating score animation SHALL appear: "+[points]" text rises 40px and fades out over 600ms in the same color as the piece placed.

---

### 3.5 Game Mode Management

**FR-MOD-001:** The game SHALL support exactly three modes: `classic`, `daily`, `zen`.

**FR-MOD-002:** Switching game modes from an active game SHALL prompt the user with a confirmation dialog ("Start new game? Current progress will be saved."). The active game state is preserved; a new game in the selected mode starts fresh.

**FR-MOD-003:** Each game mode SHALL maintain its own independent saved state in Hive, so the player can switch between Classic and Zen without losing progress in either.

**FR-MOD-004:** Classic Mode — endless, random pieces, score tracked, personal best tracked.

**FR-MOD-005:** Daily Challenge Mode — seeded by date, score tracked, sharable result, limited to one completion attempt per day per device.

**FR-MOD-006:** Zen Mode — random pieces, no score displayed, ambient music auto-plays (if music is enabled), no game over screen (game simply resets silently when no moves remain, maintaining the zen experience).

**FR-MOD-007:** The current active mode SHALL be indicated in the game screen's top bar.

---

### 3.6 Daily Challenge System

**FR-DAI-001:** The Daily Challenge SHALL use a fixed seed derived from the current device date (`yyyy-MM-dd`) to initialize the PRNG, guaranteeing the same piece sequence worldwide.

**FR-DAI-002:** The Daily Challenge SHALL reset every day at midnight local device time.

**FR-DAI-003:** A player may only complete the Daily Challenge once per calendar day. After completion, the Play button for Daily Challenge shall be replaced with "See Result" until the next day.

**FR-DAI-004:** The system SHALL display a countdown timer on the Home Screen showing time remaining until the next Daily Challenge (format: `HH:MM:SS`). The timer SHALL pulse subtly every second.

**FR-DAI-005:** Upon Daily Challenge completion, the system SHALL generate a shareable result card (see Section 3.11).

**FR-DAI-006:** The Daily Challenge completion status and score SHALL be saved to Hive keyed by date string.

**FR-DAI-007:** If the player quits mid-challenge, the state SHALL be saved and they may resume the same seed on the same day.

---

### 3.7 Progress Save/Load (Hive)

**FR-SAV-001:** All game state SHALL be serialized and saved to Hive after each successful piece placement. The system SHALL never wait for app close to save.

**FR-SAV-002:** The following data SHALL be persisted per game mode:
- Grid state (9×9 matrix of `BlockColor?`)
- Current 3 pieces in tray
- Next 3 pieces (preview)
- Current score
- Combo count
- Lines cleared count
- Blocks placed count

**FR-SAV-003:** The following global data SHALL be persisted independently of game mode:
- Best score per mode
- Lifetime stats (total lines cleared, total blocks placed, total games played)
- Current theme selection
- Daily Challenge completion log (date → score map)
- Settings (sound enabled, haptic enabled, music enabled, music volume, notifications enabled)
- Ads removed flag

**FR-SAV-004:** On app launch, the game SHALL load saved state within 200ms.

**FR-SAV-005:** If no saved state exists for a mode, the game SHALL start fresh with an empty grid and a newly generated piece set.

**FR-SAV-006:** All Hive TypeAdapters SHALL be generated via `hive_generator` and registered in `main()` before `runApp()`.

**FR-SAV-007:** Hive box names SHALL follow the schema defined in Appendix D.

### 3.8 Theme System

**FR-THM-001:** Three themes SHALL be available: `midnightZen` (default, unlocked), `desiRangoli` (locked), `arcticIce` (locked).

**FR-THM-002:** Theme selection SHALL persist across sessions via Hive.

**FR-THM-003:** Locked themes are unlocked by one of two methods:
- Reaching a score milestone (see table below)
- Watching a rewarded ad (single watch unlocks permanently)

| Theme | Score Milestone to Unlock |
|-------|--------------------------|
| Desi Rangoli | 5,000 points in Classic Mode |
| Arctic Ice | 10,000 points in Classic Mode |

**FR-THM-004:** The Themes Screen SHALL display all themes in a 2-column grid. Each card shows: theme name, 5 color swatches, and a lock icon if locked.

**FR-THM-005:** The currently selected theme SHALL have an accent-colored border glow effect on its card.

**FR-THM-006:** When a theme is unlocked, a confetti burst animation (30 colored particles, 1000ms) plays fullscreen.

**FR-THM-007:** The Home Screen background SHALL subtly reflect the currently selected theme's color palette.

**FR-THM-008:** The `ThemeCubit` SHALL expose the current `AppTheme` to the entire widget tree via `BlocProvider`.

### 3.9 AdMob Integration

**FR-ADS-001:** AdMob interstitial ads SHALL only appear on the Game Over screen, after the game over event is detected, before the game over results are shown.

**FR-ADS-002:** Interstitial ads SHALL NOT appear during gameplay under any circumstance.

**FR-ADS-003:** Banner ads SHALL NOT be used in any screen.

**FR-ADS-004:** Client-side frequency cap: no more than 1 interstitial ad per 3-minute window (180,000ms). The timestamp of the last interstitial shown SHALL be saved in memory (not Hive).

**FR-ADS-005:** If an interstitial fails to load, the game over screen SHALL show immediately without delay.

**FR-ADS-006:** The next interstitial ad SHALL begin pre-loading immediately after the previous one is shown (not after it closes).

**FR-ADS-007:** Rewarded ads SHALL be player-triggered only. The trigger is a "Hint" button on the game screen (P1 feature). The reward is revealing the optimal placement for the current highlighted piece.

**FR-ADS-008:** If the player has purchased "Remove Ads" IAP, no interstitial ads are shown. Rewarded ads remain available (player choice).

**FR-ADS-009:** AdMob unit IDs SHALL be managed via a configuration file (see Appendix C). Test IDs are used during development; production IDs are injected at release build.

**FR-ADS-010:** The `AdService` class SHALL implement `AdMobInterstitialService` and `AdMobRewardedService` interfaces and be injected via the service locator pattern.

### 3.10 IAP (Remove Ads)

**FR-IAP-001:** A single IAP product SHALL exist: "Remove Ads" (non-consumable).

**FR-IAP-002:** Product ID: `com.appwaretech.colorzen.puzzle.remove_ads`

**FR-IAP-003:** Purchase restores SHALL be supported. A "Restore Purchases" button SHALL be available in the Settings screen.

**FR-IAP-004:** The "Remove Ads" flag SHALL be stored in Hive after successful purchase verification.

**FR-IAP-005:** The `in_app_purchase` plugin SHALL handle payment and receipt validation. No custom server-side receipt validation is required for v1.0.

**FR-IAP-006:** If purchase fails, the system SHALL show a user-friendly error snackbar and make no changes to game state.

**FR-SHR-003:** The share action SHALL be triggered by the "Share Score" button on the Game Over screen (Daily Challenge mode only).

**FR-SHR-004:** `share_plus` SHALL be used to invoke the native share sheet.

**FR-SHR-005:** The generated image SHALL be saved temporarily to the app's cache directory before sharing.

### 4.4 Communication Interfaces

**FR-COM-001:** The application is fully offline-first. No network requests are made for core gameplay.

**FR-COM-002:** Network access is required ONLY for:
1. Loading and serving AdMob ads
2. IAP transaction processing (handled by platform SDK)

**FR-COM-003:** The AdMob SDK handles all ad network communication internally.

## 5. Non-Functional Requirements

### 5.1 Performance

**NFR-PER-001:** The game SHALL maintain 60fps during all animations. Measured on a Samsung Galaxy A32 (mid-range Android, 2021) as the baseline device.

**NFR-PER-002:** Cold start time (app launch → interactive Home Screen) SHALL be under 2,000ms on the baseline device.

## 6. UI/UX Specification (Complete)

### 6.1 Design Philosophy

The UI must achieve THREE psychological goals simultaneously:

1. **Instant Comprehension** — A new player must understand the core mechanic within 10 seconds with zero tutorial. The layout must communicate "drag from tray → place on grid → fill lines" through visual affordance alone.

2. **Visual Delight** — Every animation, color choice, and spacing decision must feel premium and rewarding. The game must feel more expensive than it is.

3. **Calm Focus** — The layout reduces cognitive load. The dark background recedes; the colored blocks are the star. There is breathing room around every element. Every pixel must earn its place.

**Design Principles:**
- Dark first: dark backgrounds make colored blocks pop vividly
- Generous padding: minimum 16px gutters, 24px preferred
- Rounded everything: no sharp corners; radius = 12–24px throughout
- Motion is meaning: every animation communicates game state, not just decoration
- Hierarchy through weight: scores are large and bold; labels are small and subdued

### 6.7 Responsive Considerations

The game targets screen widths from 360px (minimum) to 430px (maximum). All layout values are calculated dynamically.

| Element | 360px screen | 430px screen |
|---------|-------------|-------------|
| Cell size | (360 - 32) / 9 = 36.4px | (430 - 32) / 9 = 44.2px |
| Grid height | ~329px | ~400px |
| Piece block in tray | 36.4 × 0.85 = 30.9px | 44.2 × 0.85 = 37.6px |
| Score font | 28sp (dynamic) | 28sp (dynamic) |

**Rules:**
- No hardcoded pixel values for game elements; use `MediaQuery.of(context).size.width`.
- All text uses `sp` units, which auto-scale with system font size setting.
- Minimum tap target: 44×44 logical pixels (enforced even on small screens by using `GestureDetector` with `behavior: HitTestBehavior.opaque` and padding).
- On very tall screens (aspect ratio > 21:9), add additional `Spacer` between tray and mode switcher.

### 7.2 Difficulty Progression

ColorZen is an endless game with implicit difficulty (no explicit level numbers). Perceived difficulty increases naturally because:

1. **Grid fills up** — As pieces accumulate, the board becomes increasingly constrained. This is self-imposed by the player's strategy choices.

2. **Piece variety creates tension** — Larger pieces (4×4, T-shapes) become harder to place on a crowded board than smaller ones (monomino, domino).

3. **Color bonus incentivizes risk** — Players must decide: place a piece efficiently (easier) or hold out for a same-color line (harder but more rewarding).

4. **Combo pressure** — Maintaining combos requires planning multiple moves ahead, increasing cognitive load over time.

**There is no artificial difficulty scaling.** Piece size distribution remains constant throughout the game. The perceived difficulty arc is entirely emergent from board state.

### 7.3 Retention Mechanics

| Mechanic | Retention Goal | Implementation |
|---------|---------------|----------------|
| Daily Challenge | D1, D7, D30 retention | Seeded daily puzzle, share card, countdown timer on home screen |
| Personal Best | Competitive return | Always-visible best score, golden animation on new record |
| Theme Unlock | Long-session motivation | Score milestones at 5K and 10K unlock themes |
| Progress Save | Immediate return | Game auto-saves every move; player returns to exact state |
| Hint System (P1) | Reduce friction, reduce churn | Rewarded ad provides one optimal placement hint |
| Zen Mode | Relaxation sessions | Timer-free, score-free, ambient music drives long sessions |
| Share Card | Organic acquisition | Daily Challenge completion generates shareable image |

### 7.4 Monetization Strategy

**Revenue Streams:**

| Stream | Implementation | Frequency |
|--------|---------------|-----------|
| Interstitial ads | Game over screen | Max 1 per 3 minutes |
| Rewarded ads | Player-triggered hint | On demand |
| Remove Ads IAP | One-time purchase | Once |

**Design principles:**
- Ad experience never interrupts gameplay. Zero mid-game ads.
- Remove Ads is the only IAP. No pay-to-win, no energy systems, no premium currency.
- Rewarded ads are always optional and player-triggered. No coercion.
- The free experience is fully complete. IAP is quality-of-life, not a gate.

**Estimated LTV model:**
- Primary revenue: interstitial impressions (high-volume, casual audience)
- Secondary: rewarded ad watches (players who want hints but haven't paid)
- Tertiary: Remove Ads conversion (~2–5% of engaged players)

**BLoC Skeleton — GameBloc:**

```dart
class GameBloc extends Bloc<GameEvent, GameState> {
  final GameRepository _repo;
  final PieceGenerator _pieceGen;
  final LineClearEngine _clearEngine;
  final ScoreCalculator _scoreCalc;

  GameBloc({
    required GameRepository repo,
    required PieceGenerator pieceGen,
    required LineClearEngine clearEngine,
    required ScoreCalculator scoreCalc,
  })  : _repo = repo,
        _pieceGen = pieceGen,
        _clearEngine = clearEngine,
        _scoreCalc = scoreCalc,
        super(GameInitial()) {
    on<GameStarted>(_onGameStarted);
    on<GameLoaded>(_onGameLoaded);
    on<PiecePlaced>(_onPiecePlaced);
    on<GameReset>(_onGameReset);
  }

  Future<void> _onGameStarted(GameStarted event, Emitter<GameState> emit) async {
    emit(GameLoading());
    final session = await _repo.loadSession(event.mode) ?? _createNewSession(event.mode);
    emit(GamePlaying(session));
  }

  Future<void> _onPiecePlaced(PiecePlaced event, Emitter<GameState> emit) async {
    final currentState = state as GamePlaying;
    final newGrid = _placePiece(currentState.session.grid, event.piece, event.row, event.col);
    final clearResult = _clearEngine.detectAndClear(newGrid);
    final newScore = _scoreCalc.calculate(
      clearResult.linesCleared,
      clearResult.colorBonuses,
      currentState.session.comboCount,
    );
    
    final newSession = currentState.session.copyWith(
      grid: clearResult.grid,
      score: currentState.session.score + newScore,
      // ... update all fields
    );

    await _repo.saveSession(newSession);

    if (clearResult.linesCleared > 0) {
      emit(GameLineClear(newSession, clearResult.clearedRows, clearResult.clearedCols, newScore));
      // Allow animation to play, then continue to GamePlaying
      await Future.delayed(const Duration(milliseconds: 350));
    }

    if (_isGameOver(newSession)) {
      emit(GameOver(newSession));
    } else {
      emit(GamePlaying(newSession));
    }
  }
}
```

```dart
  [[true, true, true],
   [true, true, true],
   [true, true, true]],

  // Shape 17: Large L (3 tall, 2 wide)
  [[true, false],
   [true, false],
   [true, false],
   [true, true]],

  // Shape 18: Big horizontal bar (5 blocks)
  [[true, true, true, true, true]],

  // Shape 19: 2×3 rectangle
  [[true, true, true],
   [true, true, true]],

];
```

**Piece Weight Distribution:**
- Monomino (1 block): weight 5
- Dominoes (2 blocks): weight 15
- Trominoes (3 blocks): weight 25
- Tetrominoes (4 blocks): weight 35
- Pentominoes/Large (5+ blocks): weight 20

This ensures small pieces appear frequently enough for relief, while large pieces create challenge.
